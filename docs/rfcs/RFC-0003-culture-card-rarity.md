# RFC-0003 — افزودن فیلد اختیاری `rarity` به `CultureCard`

- **نویسنده:** AI-03
- **تاریخ:** 2026-08-22
- **وضعیت:** 🟡 در انتظار بررسی
- **نوع:** تغییر contracts

## مشکل
گنجینه (آلبوم) کارت‌های فرهنگی فعلاً همه‌ی کارت‌ها را هم‌ارزش نمایش می‌دهد.
برای انگیزه‌ی جمع‌آوری (collection loop) و جذابیت اشتراک‌گذاری، تفکیک
«کارت معمولی / کمیاب / افسانه‌ای» لازم است؛ اما `CultureCard` در
`packages/contracts/src/culture-cards.ts` چنین فیلدی ندارد و افزودن فیلد
خارج از قرارداد، خط قرمز است.

## پیشنهاد
افزودن فیلد **اختیاری** به قرارداد (backward-compatible، بدون شکستن هیچ مصرف‌کننده‌ای):

```ts
/** درجه‌ی کمیابی کارت برای گیمیفیکیشن آلبوم (اختیاری، پیش‌فرض 'common') */
export type CardRarity = 'common' | 'rare' | 'legendary';

export interface CultureCard {
  // ... فیلدهای فعلی بدون تغییر ...
  /** اختیاری؛ اگر نبود 'common' فرض شود */
  rarity?: CardRarity;
}
```

قواعد پیشنهادی محتوا (در `culture-cards` اعمال می‌شود، نه قرارداد):
- `legendary` فقط برای مناسبت‌های بزرگ (نوروز، یلدا، سده) و ابیات بسیار مشهور — حداکثر ~۵٪
- `rare` برای کارت‌های دارای `relatedWord` یا `occasionDate` — حدود ~۲۰٪
- بقیه `common`

بدون هیچ وابستگی؛ صرفاً یک union type و یک فیلد اختیاری.

## جایگزین بدون‌وابستگی بررسی‌شده
- **نگهداری rarity در فایل جداگانه داخل culture-cards** (map از id → rarity): ممکن است،
  اما UI (مالک دیگر) برای نمایش نشان کمیابی به تایپ مشترک نیاز دارد؛ بدون حضور فیلد در
  قرارداد، UI مجبور به import از داخل پکیج ما می‌شود که خلاف معماری contracts-only است.
- **استنتاج rarity در UI از روی وجود occasionDate/relatedWord:** منطق محتوایی به UI نشت می‌کند
  و قابل‌تنظیم توسط تیم محتوا نیست.

## پکیج‌های متأثر
- `packages/contracts` (افزودن type اختیاری — مالک: AI-01/نگهبان قرارداد)
- `packages/culture-cards` (تولید مقدار — مالک: AI-03)
- `packages/ui-*`/آلبوم (نمایش اختیاری نشان — بدون اجبار)

## مهاجرت
هیچ. فیلد اختیاری است؛ مصرف‌کنندگان فعلی بدون تغییر کار می‌کنند.
`validate.ts` ما پس از تأیید، مقدارهای مجاز را چک خواهد کرد.
