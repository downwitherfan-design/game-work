# 💎 سند جامع فازبندی و تقسیم کار پروژه‌ی «دُردانه»
### نسخه ۱.۰ — سند مرجع برای توسعه‌ی موازی توسط ۱۵ هوش مصنوعی مستقل

---

## بخش ۱ — چشم‌انداز محصول

**دُردانه** یک بازی معمای کلمات فارسی با فرمت روزانه است:

> «هر روز یک معمای ۶ حرفی؛ حلش کن، یک کارت فرهنگی زیبا کشف کن، نتیجه‌ات را بدون اسپویل به اشتراک بگذار، و استریکت را زنده نگه دار.»

### معادله‌ی حاکم (از سند راهبردی):
```
موفقیت = (سادگی تولید × عمق اعتیادآور × قابلیت وایرال × قالب بومی) ÷ هزینه
```

### چهار ستون تمایز:
1. **ارزان** — فقط متن و منطق؛ بدون اسکلت سه‌بعدی، بدون فیزیک.
2. **وایرال** — فرمت Daily + Streak + Share بی‌اصطکاک (مدل اثبات‌شده‌ی Wordle با ۳ میلیون کاربر در ۲ ماه بدون تبلیغ).
3. **ضدکلون** — خندق «کارت فرهنگی»: ضرب‌المثل، شعر و دانستنی ایرانی که هیچ کلون خارجی نمی‌تواند تقلید کند.
4. **مقیاس‌پذیر** — جداسازی کامل موتور از دیتابیس محتوا → صادرات با تعویض دیتابیس.

## بخش ۲ — تصمیم معماری فنی (و چرایی علمی/مهندسی آن)

### پشته‌ی انتخابی: وب‌فناوری + Capacitor (به‌جای Godot)

| معیار | Godot 4 | TypeScript + Preact + Capacitor | برنده |
|---|---|---|---|
| رندر متن فارسی (RTL، ZWNJ، اتصال حروف) | نیازمند پیکربندی HarfBuzz، پرایسک | **بومیِ مرورگر — بی‌نقص** | وب |
| توسعه‌ی موازی ۱۵ AI روی GitHub | فایل‌های صحنه‌ی باینری/tscn → تداخل merge بالا | **فایل‌های متنی + npm workspaces → مرز ماژولی دقیق** | وب |
| نسخه‌ی وب وایرال (درس 2048: بی‌اصطکاکی) | خروجی وب سنگین (~۳۰MB wasm) | **PWA زیر ۲ مگابایت** | وب |
| حجم اندروید زیر ۳۰MB (الزام سند راهبردی) | ~۲۵–۴۰MB پایه | **~۵–۸MB با Capacitor** | وب |
| پلاگین‌های بازار/مایکت/تپسل | غیررسمی و محدود | **پلاگین‌های رسمی Cordova/Capacitor موجود** | وب |
| تست خودکار (لازمه‌ی ۱۵ AI موازی) | محدود | **Vitest + Playwright بالغ** | وب |

**نتیجه:** برای یک بازی «فقط متن و منطق»، وب‌استک هم‌زمان حجم کمتر، RTL بهتر، تست‌پذیری بالاتر و — حیاتی‌تر از همه — **قابلیت توسعه‌ی موازی بدون تداخل** می‌دهد. هدف سند راهبردی (خروجی چندپلتفرمه: Android/iOS/Web/Desktop) دقیقاً حفظ می‌شود.

### معماری مونوریپو (npm workspaces)

```
My-game/
├── docs/                    ← اسناد مرجع (فقط-خواندنی برای AIها)
│   ├── 00_MASTER_PLAN.md
│   ├── 01_RED_LINES.md
│   ├── 02_CONTRACTS.md
│   └── rfcs/                ← درخواست تغییر قرارداد (تنها راه تغییر)
├── prompts/                 ← پرامپت‌های ۱۵ AI
├── packages/
│   ├── contracts/           ← 🔒 تایپ‌ها و اسکیماهای مشترک (منبع واحد حقیقت)
│   ├── core-engine/         ← AI-01: منطق خالص بازی
│   ├── word-db/             ← AI-02: دیتابیس کلمات فارسی
│   ├── culture-cards/       ← AI-03: محتوای کارت‌های فرهنگی
│   ├── ui-kit/              ← AI-04: دیزاین‌سیستم و کامپوننت‌ها
│   ├── app-shell/           ← AI-05: پوسته‌ی اپ، ناوبری، استیت
│   ├── game-board/          ← AI-06: صفحه‌ی بازی، کیبورد، انیمیشن
│   ├── viral-share/         ← AI-07: اشتراک‌گذاری و موتور وایرال
│   ├── meta-retention/      ← AI-08: استریک، آمار، دستاوردها
│   ├── backend-api/         ← AI-09: بک‌اند (Hono + Cloudflare D1)
│   ├── duel-mode/           ← AI-10: دوئل ۱به۱ (فاز ۲)
│   ├── monetization/        ← AI-11: درآمد اخلاقی (تپسل + IAP بازار)
│   ├── analytics/           ← AI-12: رصد داده و رشد
│   └── audio-haptics/       ← AI-13: صدا و لرزش
├── native/android/          ← AI-14: Capacitor، بیلد، CI/CD، انتشار
└── qa/                      ← AI-15: تست، تضمین کیفیت، i18n
```

**اصل بنیادین:** هر پکیج فقط از `packages/contracts` و پکیج‌های پایین‌دستیِ مجاز خودش import می‌کند. نمودار وابستگی یک‌طرفه است (بدون حلقه). این مرزبندی از الگوی **Conway's Law معکوس** (Team Topologies، Skelton & Pais 2019) پیروی می‌کند: ساختار کد را عمداً مطابق ساختار تیم (۱۵ AI مستقل) طراحی می‌کنیم تا ارتباط لازم بین تیم‌ها به حداقل برسد.

### نمودار وابستگی مجاز

```
contracts (بدون وابستگی)
   ↑
core-engine, word-db, culture-cards, analytics, audio-haptics  (فقط contracts)
   ↑
ui-kit (contracts) · meta-retention (contracts, core-engine)
   ↑
game-board (contracts, core-engine, ui-kit, audio-haptics)
viral-share (contracts, ui-kit)
monetization (contracts, ui-kit, analytics)
duel-mode (contracts, core-engine, ui-kit, backend-api[فقط تایپ])
   ↑
app-shell (همه — تنها نقطه‌ی مونتاژ نهایی)
backend-api (contracts — مستقل، در Cloudflare مستقر می‌شود)
```

## بخش ۳ — طراحی بازی (مشخصات قطعی)

### حلقه‌ی هسته‌ای
```
نوتیف/عادت → باز کردن اپ → معمای روزانه (کلمه‌ی ۶ حرفی، ۶ حدس)
→ حل → انیمیشن juicy + کارت فرهنگی → اشتراک بی‌اسپویلر
→ استریک +۱ / لیدربورد دوستان → (فردا دوباره)
```

### مُدهای بازی و فاز هرکدام

| مُد | توضیح | فاز |
|---|---|---|
| معمای روزانه | یک معمای ۶ حرفی مشترک برای همه، ۶ حدس | MVP |
| تمرین بی‌نهایت | معماهای نامحدود ۴ تا ۷ حرفی با دشواری پویا | MVP |
| کارت فرهنگی | ضرب‌المثل/شعر/دانستنی پس از حل + آلبوم «گنجینه» | MVP |
| دوئل آنلاین ۱به۱ | رقابت ناهمزمان با دوست از طریق لینک | فاز ۲ |
| رویداد فصلی | مسابقات زمان‌دار (یلدا، نوروز و…) | فاز ۳ |
| بسته‌های موضوعی | آشپزی، ورزش، سینما، شعر کلاسیک | فاز ۳ |

### نگاشت هر مکانیک به مبنای علمی (الزام سند راهبردی + ایده‌های افزوده)

| عنصر طراحی | مبنای علمی | منبع |
|---|---|---|
| معمای روزانه (کمیابی زمانی) | زیان‌گریزی + FOMO | Kahneman & Tversky, *Prospect Theory*, 1979 |
| استریک + Streak Freeze | حلقه‌ی عادت «مهربان» | Eyal, *Hooked*, 2014؛ مطالعات موردی Duolingo |
| اشتراک بی‌اسپویلر (گرید ایموجی) | ارز اجتماعی + عمومی‌بودن | Berger, *Contagious* (مدل STEPPS), 2013 |
| کارت فرهنگی | ارزش کاربردی + خودِ ایده‌آل + هویت | Berger 2013؛ Higgins, *Self-Discrepancy Theory*, 1987 |
| دشواری تدریجیِ تمرین | تعادل چالش↔مهارت | Csikszentmihalyi, *Flow*, 1990؛ Chen, *Flow in Games*, 2007 |
| انیمیشن حل juicy | Game Feel / Juiciness | Swink, *Game Feel*, 2008؛ Hicks et al., CHI PLAY 2019 |
| 💡 «روز دُردانه» (معمای جایزه‌دار تصادفی، ~هفته‌ای یک‌بار) | پاداش متغیر (برنامه‌ی نسبی متغیر، اعتیادآورترین زمان‌بندی پاداش) | Ferster & Skinner, *Schedules of Reinforcement*, 1957 |
| 💡 موزاییک هفتگی (هر ۷ روز استریک، یک کاشی‌کاری کامل می‌شود) | اثر پیشرفت اعطاشده + شیب هدف | Nunes & Drèze, *Endowed Progress Effect*, JCR 2006؛ Kivetz et al. 2006 |
| 💡 «گنجینه» — مرور کارت‌های فرهنگی با فاصله‌ی زمانی | اثر فاصله‌گذاری در یادگیری (کارت‌ها واقعاً آموزش می‌دهند → ارزش کاربردی برای اشتراک) | Ebbinghaus 1885؛ Cepeda et al., *Psych. Bulletin* 2006 |
| 💡 پیروزی ۳۰ ثانیه‌ای (اولین معمای هر کاربر، آسان و دست‌چین) | خودکارآمدی + قله‌ی اول تجربه | Bandura, *Self-Efficacy*, 1977 |
| 💡 پایان جلسه با نمای زیبای کارت فرهنگی | قانون قله-پایان (خاطره‌ی تجربه = قله + پایان) | Kahneman et al., *Peak-End Rule*, 1993 |
| 💡 لیدربورد «حلقه‌ی دوستان» با لینک خصوصی | نیاز به ارتباط (SDT) + مقایسه‌ی اجتماعی با افراد مشابه | Deci & Ryan, SDT, 1985؛ Festinger 1954 |
| 💡 آلبوم کارت‌های ناقص (؟ روی کارت‌های کشف‌نشده) | اثر زایگارنیک (کار ناتمام در ذهن می‌ماند) | Zeigarnik, 1927 |
| 💡 کیبورد فارسی درون-بازی با چیدمان بهینه | قانون فیتس (هدف‌های بزرگ‌تر/نزدیک‌تر = سریع‌تر) | Fitts, 1954 |
| 💡 پاسخ UI زیر ۱۰۰ms برای هر تپ | آستانه‌ی Doherty — تعامل زیر ۴۰۰ms اعتیادآور است | Doherty & Thadani, IBM 1982 |

### قواعد زبان فارسی (تصمیمات قطعی مهندسی)
- نرمال‌سازی: ي→ی، ك→ک، أ/إ/آ حفظ آ، ۀ→ه، حذف اعراب، حذف ZWNJ در مقایسه (اما حفظ در نمایش).
- «کلمه‌ی ۶ حرفی» = ۶ نویسه پس از نرمال‌سازی و حذف ZWNJ.
- منبع کلمات: واژگان پرکاربرد فارسی معیار (بدون واژه‌های توهین‌آمیز/حساس — لیست ممنوعه در word-db).

## بخش ۵ — مدل درآمد اخلاقی (قطعی)

1. **تبلیغ ویدئویی جایزه‌ای (Rewarded، تپسل):** «یک حدس اضافه» یا «راهنما». هرگز اجباری، هرگز در جلسه‌ی اول.
2. **خرید یک‌باره‌ی «نسخه‌ی طلایی»:** بدون تبلیغ + Streak Freeze نامحدود + تم طلایی انحصاری.
3. **بسته‌های محتوایی موضوعی** (محتوا، نه قدرت).
4. **تم‌های ظاهری تزئینی.**

⛔ **هرگز pay-to-win. هرگز تبلیغ اجباری. هرگز ثبت‌نام اجباری.**

## بخش ۶ — فازبندی کلان پروژه

### فاز ۰ — قراردادها و اسکلت (این سند + هفته‌ی صفر)
- خروجی: `packages/contracts` کامل، اسکلت همه‌ی پکیج‌ها، CI پایه.
- مسئول: AI-14 اسکلت مونوریپو و CI را می‌سازد؛ AI-15 تست‌هارنس قراردادها را. بقیه پکیج خالی خود را با README و تایپ‌های صادراتی مطابق قرارداد راه می‌اندازند.
- **معیار خروج:** `npm install && npm run build && npm test` در ریشه سبز باشد.

### فاز ۱ — پروتوتایپ (هفته ۱): «حال می‌دهد؟»
- core-engine کامل + game-board پایه + ۳۰۰ کلمه‌ی اولیه + یک صفحه‌ی قابل بازی در وب.
- مسئولان فعال: AI-01، AI-02، AI-04، AI-05، AI-06. بقیه: تکمیل ماژول خود پشت فلگ.
- **معیار خروج:** معمای قابل حل در مرورگر با انیمیشن فلیپ و کیبورد فارسی.

### فاز ۲ — MVP (هفته‌های ۲ تا ۵)
- معمای روزانه + تمرین بی‌نهایت + کارت فرهنگی + اشتراک + استریک + صدا + آنالیتیکس + بک‌اند روزانه + پوسته‌ی کامل + بیلد اندروید.
- همه‌ی ۱۵ AI فعال.
- **معیار خروج:** AAB امضاشده زیر ۳۰MB؛ ریتنشن D1 هدف >۴۰٪ در تست داخلی؛ حلقه‌ی کامل بدون کرش.

### فاز ۳ — انتشار نرم (هفته ۶)
- انتشار در کافه‌بازار/مایکت + وب PWA. آنالیتیکس زنده. مانیتورینگ کرش.
- **معیار خروج:** نرخ اشتراک‌گذاری >۱۵٪؛ صفر کرش بلاکر.

### فاز ۴ — رشد (هفته‌های ۷ تا ۱۲)
- دوئل ۱به۱ + لیدربورد سراسری/دوستان + بهبودهای داده‌محور + مونتیزیشن فعال.
- **معیار خروج:** ریتنشن D7 >۲۰٪.

### فاز ۵ — LiveOps و صادرات (مستمر)
- رویدادهای فصلی، بسته‌های موضوعی، معماری چندزبانه‌ی فعال‌شده (دیتابیس انگلیسی/عربی آزمایشی).

## بخش ۸ — پروتکل همکاری در GitHub

1. **شاخه‌ها:** هر AI فقط روی شاخه‌های `ai-XX/<feature>` کار می‌کند و به `main` از طریق PR مرج می‌کند (یا اگر مدیر پروژه اجازه دهد، مستقیم — اما همیشه فقط در مسیرهای مالکیت خود).
2. **کامیت‌ها:** Conventional Commits (`feat(core-engine): ...`) + کامیت‌های کوچک و پرتعداد + push فوری.
3. **تغییر قرارداد:** فقط با فایل RFC در `docs/rfcs/RFC-XXXX-title.md` و تأیید مدیر پروژه. تا تأیید، قرارداد قدیمی معتبر است.
4. **همگام‌سازی:** هر AI قبل از شروع کار `git pull --rebase origin main` می‌زند.
5. **حل تداخل:** چون مسیرها ناهمپوشان‌اند، تداخل merge فقط در `package-lock.json` ممکن است → قانون: فقط AI-14 حق commit کردن lock-file را دارد؛ بقیه وابستگی جدید را در RFC درخواست می‌کنند.
