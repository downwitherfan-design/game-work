# 📦 سیاست وابستگی‌ها — «صفر وابستگی مگر با توجیه»

### چرا سخت‌گیر هستیم؟
- هر KB به حجم AAB (سقف سخت: **30MB**) و به بوت سرد (سقف: **< 2 ثانیه**) ضربه می‌زند.
- پژوهش Doherty (1982): زیر ۴۰۰ms پاسخ‌دهی، بهره‌وری کاربر جهش می‌کند.
- آمار Google: هر **۱۰۰ms تأخیر** در بارگذاری = افت محسوس نرخ تبدیل/ماندگاری.
- بودجه‌ی وب: باندل اولیه **< 2MB gzip** — گارد CI (`tools/check-budget.mjs`) عبور از آن را fail می‌کند.

### قانون
1. **پیش‌فرض: نه.** هر وابستگی جدید (dependencies یا devDependencies هر workspace) فقط با
   **RFC در `docs/rfcs/`** اضافه می‌شود.
2. فقط **AI-14** حق commit روی `package.json` ریشه و `package-lock.json` را دارد.
3. هر RFC وابستگی باید شامل باشد:
   - نام و نسخه‌ی دقیق (pin — بدون `^` و `~`)
   - **حجم**: minified + gzip (از bundlephobia) و اثر تخمینی روی AAB
   - جایگزین بدون‌وابستگی که بررسی و رد شده (چرا نوشتن ۵۰ خط خودمان کافی نبود؟)
   - سطح نگهداری (آخرین release، تعداد وابستگی‌های transitive)
4. معیار رد سریع:
   - وابستگی transitive > 5 → رد مگر توجیه استثنایی
   - > 20KB gzip برای کاری که با < 200 خط کد قابل نوشتن است → رد
   - polyfill چیزهایی که ES2020/WebView مدرن دارد → رد
5. **devDependencies** هم مشمول‌اند (سرعت CI و قطعیت بیلد) اما آستانه‌ی سخت‌گیری کمتر است.

### بیلدهای قطعی (Reproducible)
- همه‌ی نسخه‌ها **pin دقیق**؛ `package-lock.json` همیشه commit می‌شود (فقط AI-14).
- CI فقط `npm ci` (هرگز `npm install`) — بیلد قطعی، همان فلسفه‌ی معمای قطعی روزانه.
- ارتقای نسخه = RFC مثل وابستگی جدید (بازبینی changelog امنیتی/حجمی).

### فرایند عملی
1. AI متقاضی: `docs/rfcs/RFC-XXXX-dep-<name>.md` می‌سازد (قالب: `docs/rfcs/TEMPLATE.md`).
2. AI-14 بررسی می‌کند: حجم، جایگزین‌ها، نگهداری.
3. در صورت تأیید: AI-14 آن را pin شده به workspace مربوط اضافه و lock را commit می‌کند.
4. رد شده؟ دلیل داخل همان RFC ثبت می‌شود.
